## 1. Контекст и цели

### 1.1 Проблема
Грейдирование сейчас идёт через Excel-шаблон «Скиллсет 2.0». Минусы:
- ~50 полей в одном листе, лид легко ошибается.
- Нет шаринга с дизайнером в виде «портрета».
- Нет версионирования и аудита.
- Любая правка матрицы (вес, гейт, новый навык) — копирование файла, ручной перерасчёт, риск расхождений.

### 1.2 Цели v1
1. Снять с лида рутину расчёта XP, проверки гейтов, формирования диаграмм.
2. Дать дизайнеру прозрачный портрет с понятной картой развития.
3. Сделать матрицу управляемой — Admin меняет в UI, не правит файл.
4. Зафиксировать историю оценок (кто, когда, что менял).
5. Поддержать переход со старой системы грейдов **без отката уровней** (grade floor).

### 1.3 Метрики успеха через 3 месяца после запуска
- ≥80% дизайнеров отдела имеют опубликованную оценку за цикл.
- Время заполнения одной оценки лидом: ≤30 минут.
- 0 расхождений между расчётом приложения и контрольным расчётом в Excel на эталонных профилях.
- Лид не возвращается к Excel-шаблону.

### 1.4 Цикл оценки
**2 раза в год: апрель и октябрь.** Между циклами — черновик и заметки. Публикация → новый «текущий» портрет, предыдущий уходит в архив.

### 1.5 Out of scope для v1
- Самооценка дизайнера + загрузка фигма-файлов как доказательств.
- Иконки навыков, кастомная инфографика.
- ИПР с уровня Мидл.
- Интеграция с Tims / 1С / другими HR.
- Mobile-приложение.
- Push/email-уведомления (кроме служебных от Keycloak).
- Перерасчёт публикованных оценок при правке матрицы (snapshot защищает).

## 3. Use cases (краткие)

См. v0.2 PRD — все use cases актуальны. Новое:

### UC7: Admin деактивирует/удаляет навык
1. Admin открывает матрицу, видит навык как «Активен» (тоггл включен).
2. Выключает тоггл → навык переходит в «Архив».
   - В форме оценки больше не показывается.
   - В существующих snapshot-портретах остаётся (там данные заморожены).
   - В новых оценках не учитывается.
3. **Удаление возможно только из архивных навыков**, кнопкой «Удалить N архивных навыков» в матрице.
4. При удалении: предупреждение «Это удалит навык и из старых snapshot-оценок. Старые портреты могут немного измениться, XP пересчитается без них». Требует явного подтверждения.

### UC8: Admin понижает grade_floor дизайнера
1. Admin открывает карточку дизайнера в `/admin/users/[id]`.
2. Видит текущий grade_floor (например, «Мидл»).
3. Меняет на более низкий (например, «Джун+»).
4. Confirm: «Это понизит зафиксированный грейд. Действие логируется. Продолжить?».
5. Изменение пишется в audit log с до/после/обоснованием.

## 6. Бизнес-логика

### 6.1 Расчёт XP
```
xp_per_skill = (skill.active ? mastery_level × weight[designer.build] : 0)
total_xp = sum(xp_per_skill) по всем активным навыкам
```
**Деактивированные навыки выключены из расчёта.** Это значит: если навык был активен в момент публикации старой оценки и есть в snapshot — там он остаётся как есть (snapshot заморожен). В новой оценке он просто не появится в форме.

### 6.2 Пороги XP (entry to grade) — единые для всех билдов
| Грейд | Порог XP |
|-------|----------|
| Intern | < 0 (не начато) |
| Junior | 0+ |
| Junior+ | 70+ |
| Middle | 120+ |
| Middle+ | 180+ |
| Senior | 230+ |

### 6.3 Effective grade и grade floor
```
effective_grade = max_by_sort(calculated_grade, designer.grade_floor)
```
**Правила:**
- Floor задаёт Lead или Admin при создании/редактировании дизайнера.
- Floor можно **повысить** (Lead/Admin) и **снять** (Admin).
- **Понижение floor — только Admin, с явным подтверждением + audit-лог запись (action: `grade_floor_lowered`, before/after/reason).**
- Снятие floor — только Admin, с подтверждением + audit-лог (`grade_floor_removed`).

### 6.4 Версионирование матрицы
- **Любая правка матрицы → новая MatrixVersion.** Нет деления на «косметические» и «структурные» — всё одинаково (упрощает аудит).
- Опубликованные оценки **не пересчитываются** — snapshot защищает.
- Черновики на старой версии получают плашку «Матрица обновлена. Перенести на v[N+1]?».
- При переносе черновика: если в новой версии каких-то навыков нет (удалены) — показать предупреждение «N оценок будут потеряны» с подтверждением.

### 6.5 Жизненный цикл навыка
1. **Создан** → `active = true`, в текущей версии матрицы.
2. **Деактивирован** (тоггл) → `active = false, archivedAt = now()`.
   - Не показывается в форме оценки.
   - Не учитывается в расчёте XP в новых оценках.
   - В старых snapshot-портретах остаётся.
3. **Удалён** (только из архива, кнопкой «Удалить N архивных навыков»):
   - Каскадно удаляется из всех таблиц текущей версии (Skill, SkillWeight, MasteryLevel, SkillGate).
   - В старых snapshot-портретах — навык исчезает (XP пересчитывается без него; **видимость портрета может измениться**, дизайнеру показывается короткое уведомление в портрете).
   - Запись в audit-лог с указанием, какие snapshot-портреты были затронуты.

### 6.6 Заметки лида
- Свободный текст до 5000 знаков.
- Видны только Lead/Admin. Не видны дизайнеру.
- Привязка к designer, не к assessment — переживают циклы.
- Изменения логируются в DesignerNote с историей.

- В форме оценки лид-сторона видит блок «Самооценка дизайнера» рядом со скиллом. Несовпадение подсвечивается.

**Модель данных:**

```

                createdAt }
SelfAssessment { id, designerId, skillId, level, comment,
                 updatedAt }
```

**Критерий приёмки:** дизайнер прикладывает материалы и ставит самооценку из портрета; лид видит и материалы, и самооценку при грейдировании; разница «лид/самооценка» визуально подсвечена.

### 11.8. Phase 16 — Подгрузка перформанса и стоимости дизайнера

К каждой форме оценки (`/lead/assess?id=X`) подгружать внешние метрики дизайнера за прошедший период:

- Часы по проектам (из учёта времени)
- Скорость / итерации правок
- NPS / отзывы клиентов
- Выполнение OKR / целей

**Источник данных:** API-интеграция с системой учёта (название уточнит Pavel) либо ручной импорт CSV. На MVP-этапе — выделенный блок «Перформанс» в боковой панели формы оценки, лид видит цифры рядом со скиллами и опирается на них при выставлении уровней.

#### Стоимость дизайнера (зарплата) — отдельный pillar

Помимо перформанса в систему добавляется приватный показатель — **стоимость дизайнера**:

- **Хранение:** новое поле `User.salaryRub` (или отдельная таблица `SalaryHistory` если важна история — решим при имплементации). Источник — ручной ввод админом или импорт из 1C/HR-системы.
- **Видимость по ролям:**
  - **admin** — точная сумма в рублях.
  - **lead** — индекс из 6 ступеней: «очень дешёвый / дешёвый / средний / дорогой / очень дорогой / максимальный». Конкретные пороги диапазонов — отдельный конфиг, считается процентилями по всей команде дизайна.
  - **stardiz, designer** — не видят вообще, **но** показатель **учитывается** в их позиции в лидерборде.
- **Где показывается:**
  - Карточка дизайнера / popup-360°: admin — поле «ЗП», lead — индекс.
  - Форма оценки `/lead/assess`: индекс — в блоке «Перформанс».
  - Лидерборд — отдельной колонки нет; влияет только через формулу ранжирования (см. ниже).

#### Формула лидерборда — итог

Сейчас в лидерборде сортировка по чистому XP. После Phase 16 позиция определяется композитной метрикой, учитывающей **три pillar'а**:

1. **XP** — компетенции (видно всем, уже считается).
2. **Перформанс** — нормализованный индекс из внешних метрик (часы / скорость / NPS / OKR). Виден всем.
3. **Стоимость** — отрицательный вклад: чем дороже при тех же XP и перформансе, тем ниже в рейтинге. Виден только admin (в рублях) и lead (как индекс).

Конкретная формула обсуждается отдельно, как минимум направление:
`score = α · XP_norm + β · Perf_norm − γ · Cost_norm`
где `α, β, γ ≥ 0`, нормировка — `0..1` по команде на момент расчёта.

**Решения (Pavel, 11 мая 2026):**
- **Дизайнер** не видит ни своего `score`, ни своей позиции в лидерборде. (У него и так нет доступа к `/admin/users`; дополнительно — никаких намёков на ранжирование в `/designer`.)
- **Stardiz** не видит свою стоимость-индекс. Видимость стоимости остаётся только у admin (₽) и lead (индекс).
- **Нет данных перформанса** — дизайнер **исключается из лидерборда** (и из расчёта `score`), даже если зарплата задана. Перформанс — обязательный сигнал для попадания в ранжирование.
- **Веса α/β/γ — фиксированные константы.** Хардкод в коде / config. Подбираем эмпирически при имплементации, без UI настройки.

**Критерий приёмки:** на форме оценки есть блок с фактическими метриками за период; на карточке/popup дизайнера видна стоимость в форме, соответствующей роли смотрящего; лидерборд сортируется по композитной формуле и не показывает дизайнеров без перформанса.

### 11.9. Phase 17 — ИПР (индивидуальный план развития)

ИПР — структурированный документ роста, который лид (или стардиз) составляет для дизайнера. Привязан к одной или нескольким опубликованным оценкам.

**Состав ИПР:**

- **Цель грейда** на следующий цикл (например, «дойти до Мидл за 6 месяцев»)
- **Сильные стороны** — что хорошо получается (импорт из портрета — последняя оценка)
- **Зоны роста** — конкретные навыки/группы, которые нужно подтянуть
- **Шаги** — список задач/практик с дедлайнами и статусом (todo / in-progress / done)
- **Чек-ин даты** — когда лид со стардизом смотрят прогресс

**Видимость:** дизайнер видит свой ИПР и может отмечать шаги выполненными; лид/стардиз — редактирует. История ИПР сохраняется по циклам.

**Модель данных (черновик):**

```
DevelopmentPlan { id, designerId, authorId (lead/stardiz),
                  cycleLabel, targetGrade,
                  strengths: text, growthAreas: text,
                  createdAt, updatedAt, status }
DevelopmentPlanStep { id, planId, title, description, dueAt,
                      status, doneAt, comment }
```

**Критерий приёмки:** лид/стардиз создаёт ИПР, добавляет шаги, дизайнер видит свой ИПР в `/designer/development-plan` и отмечает шаги.

### 11.13. Phase 21 — Метрическая система оценки команды (на обсуждение)

**Цель.** Переложить корпоративную метрическую систему оценки бизнеса IDA на дизайн-команду, чтобы лиды и c-level смотрели на дизайн через те же категории, что и на компанию в целом — но с метриками, имеющими смысл именно для дизайна.

**Эта фаза — концепт.** Описывает направление, не готовую спецификацию. Решения по формулам, источникам данных и UI принимаем итеративно — этот раздел и есть точка отсчёта обсуждения.

#### Корпоративная система (5 категорий, как у IDA)

| # | Категория | Что внутри (на уровне компании) |
|---|---|---|
| 1 | **Прибыльность** | Выручка, Gross Profit, EBITDA, Return on Capital |
| 2 | **Траст / Репутация** | Кол-во негативных отзывов по каналам, негативных медиа-новостей, жалоб клиентов, нарушений по аудитам |
| 3 | **Dream Team** | NIPC = (% «выше ожиданий» − % «ниже ожиданий»). Доп. метрики: точность найма (доля прошедших испытательный срок), доля уходов из-за выгорания |
| 4 | **Качество продукта** | Продуктовые метрики (зависят от продукта) |
| 5 | **Best Product** | Соотношение использования продукта (для нас — приход клиентов) |

#### Перекладка на дизайн-команду (4 категории)

| # | Категория для дизайна | Из чего собираем | Уже есть в системе? |
|---|---|---|---|
| 1 | **Эффективность / Перформанс** | Текущий грейд каждого дизайнера, средний грейд команды, средний XP, скорость роста (XP per цикл) | ✅ есть (Assessment + Phase 15 — график скорости роста) |
| 2 | **Траст / Репутация** | NPS дизайн-сервиса от клиентов, текстовые отзывы клиентов, кол-во уходов клиентов, кол-во переходов проектов в Improve | ❌ нет, новые сущности |
| 3 | **Dream Team** | Распределение по 9-Box (% «звёзд», «основы», «ошибки подбора», NIPC по матрице потенциала) | ✅ частично (TeamMatrixCell — Phase 9) |
| 4 | **Качество результата** | Субъективная оценка дизайн-лидов и c-level на регулярном интервале (rolling assessment, например раз в квартал) | ❌ нет, новая сущность |

#### Что нужно решить (вместе)

**По данным:**
- Откуда берём NPS — внешняя система или собираем формой в этом же приложении? Опрос клиентов после сдачи проекта — встраиваем или просто импортируем числа?
- «Уход клиента» и «переход в Improve» — это про конкретного клиента/проект (нужно завести `Project` сущность?) или агрегат за период (поле в `TeamMetricSnapshot`)?
- «Субъективная оценка c-level» — кто, как часто, по какой шкале? Скорее всего регулярный шаг (квартал) с фиксированной формой; формат — отдельная сущность типа `LeadershipReview { reviewerId, designerId, period, score, comment }`.
- 9-Box — берём snapshot на момент расчёта или текущее состояние? (для исторических графиков нужны snapshot'ы)

**По формулам:**
- NIPC для дизайна — считаем по 9-Box или по результатам ассессментов («выше/на уровне/ниже ожиданий» = эфф. грейд vs. ожидаемый по сроку работы)?
- Как агрегировать 4 категории в общий «здоровье команды» индекс — взвешенная сумма? Радар-чарт без агрегата? Pavel: вероятно радар, без единого числа (опасно сводить к «оценке департамента одной цифрой»).

**По UI:**
- Где живёт дашборд: новая вкладка в `/admin/users` (рядом с «9-Box»), отдельный раздел `/admin/team-health`, или модуль на главной для admin/lead?
- Гранулярность: метрики на команду целиком, на отдел (Inhouse/Create/Improve), на конкретного лида с его подопечными — или всё сразу с фильтром?
- Что админ может **сделать** на этом дашборде, кроме «смотреть»? Drill-down в конкретных дизайнеров? Экспорт?

**По интеграциям:**
- Прибыльность не считаем сами (это домен финансов), но возможно подтянуть из существующих систем IDA — есть ли API? Или это «out of scope» дизайн-приложения.

#### Гипотеза по поэтапной реализации (черновая)

1. **Phase 21.1** — снапшот 9-Box + NIPC. Сохраняем состояние матрицы потенциала в `TeamMatrixSnapshot` (jsonb с распределением) раз в N дней автоматически. Это даёт исторический график и индекс Dream Team без новых форм.
2. **Phase 21.2** — `LeadershipReview` — форма для c-level. Раз в квартал каждый руководитель выставляет каждому дизайнеру оценку по простой шкале + комментарий. Агрегат → метрика «Качество результата».
3. **Phase 21.3** — встроенный NPS-опросник на финале проектов. Простейший: email с одним вопросом «оцените от 0 до 10». Хранится в `ClientFeedback`.
4. **Phase 21.4** — дашборд `/admin/team-health` с радар-чартом по 4 категориям + drill-down в источники.
5. **Phase 21.5** — (опционально) подтяжка прибыльности из корпоративных систем, если получится договориться по API.

**Критерий приёмки.** Лид/c-level открывает один экран и за 30 секунд понимает: где команда сильна, где деградирует, на каких людей делать ставку, кому нужна помощь.

**Зависимости.** Опирается на: Phase 9 (9-Box → Dream Team), Phase 15 (скорость роста → Эффективность), будущий Phase 14 (самооценка + evidence → объективность Качества результата).

### 11.14. Phase 22 — Оценка лидов и стардизов через 360-опрос

Лидов и стардизов нельзя оценить по 51-навыковой матрице — их работа другого характера. Используем формализованный **360-опрос команды + KPI + CDO-оценку**. Результат — сводный «Отчёт по лиду/стардизу» того же визуального уровня, что и портрет дизайнера, но с другой структурой.

**Кто кого оценивает:**
- **Лидов** оценивает админ.
- **Стардизов** оценивает админ или их прямой лид.
- **Опрос заполняют** менеджеры, дизайнеры (свои подопечные и кросс-функциональные), фронтендеры или лиды фронтенда — все, кто реально работал с этим лидом за период.

**Как процесс выглядит сейчас (вручную):**
1. Pavel рассылает Google Form по списку респондентов.
2. Ответы экспортируются и руками собираются в BuildIn-документ.
3. ИИ (Gemini / ChatGPT) генерирует раздел «Выводы» из агрегированных ответов.
4. Pavel вручную пишет блок «CDO»: KPI на период (фиксируются/корректируются раз в полгода), наблюдения, итоговая оценка результатов.

**Как переносим в инструмент (решение Pavel'a от 11.05.2026):**
Сбор ответов **остаётся в Google Form** — это вне инструмента. Сам опрос всегда **полностью анонимный**: респондентам не нужно логиниться в наш сервис, magic-link не делаем. Инструмент получает уже **готовый CSV-экспорт** ответов на старте нового цикла оценки лида/стардиза. Дальше он считает агрегаты, генерит ИИ-выводы и склеивает финальный отчёт.

**Ритм:** ad-hoc по запросу админа, как у дизайнеров (сезонные грейдирования). Для лидов/стардизов на испытательном — каждые 3 месяца от даты найма.

**Структура опроса (категории, по примеру Артуша Манукяна 12.2025):**

1. **Качество ревью и техническая экспертиза** (≈5 пунктов, 1–5): высокий план по UI, структурное ревью, минимум возвратов, баланс вкус/бренд/прибыль, проработка состояний/сетки/паттернов. + текстовое поле «что помогает / мешает».
2. **Процессы** (≈4 пункта, 1–5): попадание в эстимейты, контроль «хвостов», проверка состояний/адаптива/экспорта, коммуникация с РМ и фронтом. + текст «где сыпется чаще всего».
3. **Развитие команды** (≈4 пункта, 1–5): понятные цели роста, обратная связь, ускорение через шаблоны/приёмы, «у кого учиться». + текст «чему конкретно научились».
4. **Продуктовое мышление** (≈3 пункта, 1–5): понимание цели экрана/фичи, варианты А/Б, отстаивание решений перед клиентом. + текст с примером.
5. **Коммуникация и софт-скиллы** (≈4 пункта, 1–5): уважительность, фиксация договорённостей, доступность, поддержка команды. + текст «что сохранить / поменять» и пример дискомфорта.
6. **Качество результата** (≈3 пункта, 1–5): учёт состояний, синхронизация паттернов, работа с фронтом/QA. + текст «какие нестыковки повторяются».
7. **Готовность работать дальше** (1 пункт, шкала 1–10).
8. **Открытые вопросы:** 3 сильные стороны · 3 зоны роста · «что бы сделал первым делом на месте лида» · общие переживания про дизайн в команде.

#### Поэтапная разбивка

**Phase 22.1 — Модель и импорт CSV.**
- Сущности: `LeadReview { id, targetUserId, period, status, createdById, importedAt, rawCsv, aggregates, aiSummary, cdoSummary, publishedAt }`. Сводные числа и текстовые ответы хранятся в `aggregates: jsonb` (структура повторяет дерево категорий) — без отдельной таблицы респондентов, поскольку они анонимны.
- Админ нажимает «Новая оценка лида» → выбирает таргет (lead/stardiz) и период → загружает CSV-экспорт Google Form. Парсер маппит колонки в категории-пункты, считает средние, собирает текстовые ответы в массивы.
- В сыром виде CSV сохраняется в `rawCsv` (text) — на случай перепарса при изменении логики.

**Phase 22.2 — Агрегирование и отчёт.**
- Средние арифметические по пунктам и по категориям. Общий балл по категории — среднее её пунктов.
- Текстовые ответы — без имён респондентов (анонимно), просто массив строк с подсчётом «N респондентов ответили».
- Экран `/admin/lead-review/[id]`: шапка (имя/период/средний NPS) → блоки категорий с подитогом и детализацией → список текстовых комментариев → готовность работать.
- Дизайн повторяет вёрстку портрета дизайнера: те же чипы, типографика, аккордеоны, иконки.

**Phase 22.3 — ИИ-выводы.**
- Кнопка «Сгенерировать выводы» в админ-режиме. LLM получает агрегаты + анонимные тексты, возвращает «Сильные стороны» и «Зоны роста» — в духе текущего ручного отчёта.
- Сохраняется как `LeadReview.aiSummary` (markdown). Админ может перегенерить или править вручную.

**Phase 22.4 — CDO-блок.**
- Pavel заполняет вручную: KPI периода, наблюдения, итоговая оценка. Сохраняется как `LeadReview.cdoSummary` (markdown).
- Формат KPI (отдельная сущность `LeadKPI` или просто markdown) — решим перед стартом фазы.

**Phase 22.5 — Видимость и экспорт.**
- Видимость: админ — всегда. Сам лид/стардиз — **сразу с момента создания записи**, без отдельной публикации (Pavel: «может видеть сразу»). Другие — нет.
- Кнопка «Скачать PDF» с финальным отчётом — для админа и для самого лида.

#### Решения зафиксированы (Pavel, 11.05.2026)

- **Анонимность респондентов — полная.** В UI инструмента нигде не показываем кто что ответил; только агрегаты + массив анонимных текстовых ответов.
- **Без входа на сервис.** Опрос остаётся в Google Form, импорт CSV.
- **Ритм** — ad-hoc по запросу админа. Для лидов/стардизов на испытательном — каждые 3 мес.
- **Видимость лиду — сразу**, без отдельной публикации.

#### Что закрыто в Phase 22.1 (11.05.2026)

Модель `LeadReview` + парсер CSV + страницы портрета лида:

- **Модель данных:** `LeadReview { targetUserId, period, surveyVersion, responseCount, rawCsv, aggregates(json), aiSummary?, cdoSummary?, createdById, importedAt }`. Без `status`/`publishedAt` — Pavel явно попросил «видимость сразу».
- **Шаблон опроса v1** — захардкожен в `src/lib/leadSurvey.ts` (6 категорий с 23 числовыми пунктами + eNPS + 4 открытых вопроса). Названия категорий взяты из реального отчёта по Артушу (12.2025), не из этого PRD — чтобы совпадать с живой практикой Pavel'a.
- **CSV-парсер** — `src/lib/parseLeadReviewCsv.ts`. Маппинг через точный текст вопроса (нормализация пробелов). Игнорирует пустые ответы при расчёте средних. Сохраняет `rawCsv` для возможного перепарса при поднятии `surveyVersion`.
- **API:** POST `/api/lead-reviews` (admin), PATCH/DELETE `/api/lead-reviews/[id]` (admin).
- **UI вход:** в попап-карточке 360° (UserCard360) для лидов и стардизов появляются кнопки «Открыть портрет» (admin или сам лид) и «Импортировать опрос» (admin).
- **Страница портрета:** шапка с переключателем циклов (segmented control), карточка eNPS с разбивкой по ролям, 6 категорий-секций (числа + прогресс-бары + аккордеон открытых ответов), сравнительная таблица «роли × категория», открытые вопросы, AI-сводка (markdown textarea), CDO-блок (markdown textarea).
- **Навигация:** лид/стардиз получили пункт «Мой портрет» в хедере — ведёт на свежую LeadReview или пустую страницу с подсказкой.

**Отложено в Phase 22.2+:**
- 22.2 — sparkline-прогрессия средних между циклами (Pavel явно попросил подумать как выводить рост между грейдированиями).
- 22.3 — автоматическая ИИ-генерация `aiSummary` (сейчас Pavel прогоняет агрегаты через ChatGPT/Gemini снаружи и вставляет markdown).
- 22.4 — структурированный CDO-блок (KPI как отдельная сущность с целевыми/фактическими значениями).
- 22.5 — PDF-экспорт + reminder каждые 3 мес для лидов на испытательном.

#### Решения «обсудим перед стартом фазы»

- Состав респондентов — фиксированный список ролей или гибкий per-цикл?
- KPI — отдельная сущность с целевыми/фактическими значениями или просто markdown в cdoSummary?
- Версионирование вопросов — если шаблон опроса меняется со временем, как сравнивать предыдущие циклы (заморозка в `LeadReview` или сквозная нумерация).

**Связь с другими фазами.** Phase 22 — независимая, не блокирует другие. Её результаты (средняя оценка лида) можно вписать в композитную метрику Phase 21 («Качество результата» для лидов — это Phase 22).
