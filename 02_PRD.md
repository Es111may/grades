## 1. Контекст и цели

### 1.1 Проблема
Грейдирование сейчас идёт через Excel-шаблон «Скиллсет 2.0». Минусы:
- ~50 полей в одном листе, лид легко ошибается.
- Нет шаринга с дизайнером в виде «портрета».
- Нет версионирования и аудита.
- Любая правка матрицы (вес, гейт, новый навык) — копирование файла, ручной перерасчёт, риск расхождений.

### 1.2 Цели v1
1. Снять с лида рутину расчёта XP, проверки гейтов, формирования диаграмм.
2. Дать дизайнеру прозрачный портрет с понятной картой развития.
3. Сделать матрицу управляемой — Admin меняет в UI, не правит файл.
4. Зафиксировать историю оценок (кто, когда, что менял).
5. Поддержать переход со старой системы грейдов **без отката уровней** (grade floor).

### 1.3 Метрики успеха через 3 месяца после запуска
- ≥80% дизайнеров отдела имеют опубликованную оценку за цикл.
- Время заполнения одной оценки лидом: ≤30 минут.
- 0 расхождений между расчётом приложения и контрольным расчётом в Excel на эталонных профилях.
- Лид не возвращается к Excel-шаблону.

### 1.4 Цикл оценки
**2 раза в год: апрель и октябрь.** Между циклами — черновик и заметки. Публикация → новый «текущий» портрет, предыдущий уходит в архив.

### 1.5 Out of scope для v1
- Самооценка дизайнера + загрузка фигма-файлов как доказательств.
- Иконки навыков, кастомная инфографика.
- ИПР с уровня Мидл.
- Интеграция с Tims / 1С / другими HR.
- Mobile-приложение.
- Push/email-уведомления (кроме служебных от Keycloak).
- Перерасчёт публикованных оценок при правке матрицы (snapshot защищает).

## 3. Use cases (краткие)

См. v0.2 PRD — все use cases актуальны. Новое:

### UC7: Admin деактивирует/удаляет навык
1. Admin открывает матрицу, видит навык как «Активен» (тоггл включен).
2. Выключает тоггл → навык переходит в «Архив».
   - В форме оценки больше не показывается.
   - В существующих snapshot-портретах остаётся (там данные заморожены).
   - В новых оценках не учитывается.
3. **Удаление возможно только из архивных навыков**, кнопкой «Удалить N архивных навыков» в матрице.
4. При удалении: предупреждение «Это удалит навык и из старых snapshot-оценок. Старые портреты могут немного измениться, XP пересчитается без них». Требует явного подтверждения.

### UC8: Admin понижает grade_floor дизайнера
1. Admin открывает карточку дизайнера в `/admin/users/[id]`.
2. Видит текущий grade_floor (например, «Мидл»).
3. Меняет на более низкий (например, «Джун+»).
4. Confirm: «Это понизит зафиксированный грейд. Действие логируется. Продолжить?».
5. Изменение пишется в audit log с до/после/обоснованием.

## 6. Бизнес-логика

### 6.1 Расчёт XP
```
xp_per_skill = (skill.active ? mastery_level × weight[designer.build] : 0)
total_xp = sum(xp_per_skill) по всем активным навыкам
```
**Деактивированные навыки выключены из расчёта.** Это значит: если навык был активен в момент публикации старой оценки и есть в snapshot — там он остаётся как есть (snapshot заморожен). В новой оценке он просто не появится в форме.

### 6.2 Пороги XP (entry to grade) — единые для всех билдов
| Грейд | Порог XP |
|-------|----------|
| Intern | < 0 (не начато) |
| Junior | 0+ |
| Junior+ | 70+ |
| Middle | 120+ |
| Middle+ | 180+ |
| Senior | 230+ |

### 6.3 Effective grade и grade floor
```
effective_grade = max_by_sort(calculated_grade, designer.grade_floor)
```
**Правила:**
- Floor задаёт Lead или Admin при создании/редактировании дизайнера.
- Floor можно **повысить** (Lead/Admin) и **снять** (Admin).
- **Понижение floor — только Admin, с явным подтверждением + audit-лог запись (action: `grade_floor_lowered`, before/after/reason).**
- Снятие floor — только Admin, с подтверждением + audit-лог (`grade_floor_removed`).

### 6.4 Версионирование матрицы
- **Любая правка матрицы → новая MatrixVersion.** Нет деления на «косметические» и «структурные» — всё одинаково (упрощает аудит).
- Опубликованные оценки **не пересчитываются** — snapshot защищает.
- Черновики на старой версии получают плашку «Матрица обновлена. Перенести на v[N+1]?».
- При переносе черновика: если в новой версии каких-то навыков нет (удалены) — показать предупреждение «N оценок будут потеряны» с подтверждением.

### 6.5 Жизненный цикл навыка
1. **Создан** → `active = true`, в текущей версии матрицы.
2. **Деактивирован** (тоггл) → `active = false, archivedAt = now()`.
   - Не показывается в форме оценки.
   - Не учитывается в расчёте XP в новых оценках.
   - В старых snapshot-портретах остаётся.
3. **Удалён** (только из архива, кнопкой «Удалить N архивных навыков»):
   - Каскадно удаляется из всех таблиц текущей версии (Skill, SkillWeight, MasteryLevel, SkillGate).
   - В старых snapshot-портретах — навык исчезает (XP пересчитывается без него; **видимость портрета может измениться**, дизайнеру показывается короткое уведомление в портрете).
   - Запись в audit-лог с указанием, какие snapshot-портреты были затронуты.

### 6.6 Заметки лида
- Свободный текст до 5000 знаков.
- Видны только Lead/Admin. Не видны дизайнеру.
- Привязка к designer, не к assessment — переживают циклы.
- Изменения логируются в DesignerNote с историей.

> Phase 6+ — план развития после MVP. Порядок ориентировочный, приоритеты обсуждаемые.

### 11.1. Phase 6 — Production auth (Keycloak / SSO)

Сейчас прод работает на dev-auth (`AUTH_MODE=dev`) — пользователь выбирает аккаунт из списка без пароля. Перед раскаткой на всю команду нужна нормальная авторизация.

**В коде уже сделана подготовка** — NextAuth настроен на провайдер по `AUTH_MODE`. Для боевого режима нужно либо:

- поднять Keycloak и подсунуть `KEYCLOAK_ISSUER` / `_CLIENT_ID` / `_CLIENT_SECRET` (готово в `auth.ts`); либо
- заменить провайдер на корпоративный SSO (Google Workspace OAuth, magic-link через email и т.п.) — Pavel выберет на основе того, что уже стоит в IDA.

**Критерий приёмки:** все логины идут через корпоративный identity provider, dev-mode остаётся доступен только локально.

### 11.2. Phase 7 — Канбан-доска пользователей

Заменить таблицу `/admin/users` (или дополнить альтернативной view) на канбан в стиле Notion/Linear.

**Поведение** (по референсу IDA-внутрянки, скриншот пользователя):

- Колонки = отделы (Импрув / Криэйт / Инхаус / Лид)
- Карточки = пользователи (аватар, имя, бэйдж непрочитанного и т.п.)
- Drag-and-drop карточки между колонками = смена отдела (с записью в audit-log)
- Переключатели view: «Отделы» / «Лиды» / «Уровни» (group-by разный)
- Inline `+ New` в каждой колонке — быстрое создание

**Критерий приёмки:** админ видит компанию как канбан, может перемещать дизайнеров между отделами, переключать ось группировки.

### 11.3. Phase 8 — Роль «Стардиз»

Новая роль наравне с `lead`. Стардиз = опытный дизайнер, у которого нет своих подопечных, но он:

- Имеет права лида: оценивает других дизайнеров, читает портреты, составляет ИПР
- Сам остаётся **грейдируемым** — лид может его оценить и поднимать ему грейд
- Может вести ИПР для назначенных ему дизайнеров (см. 11.5)

**Изменения в схеме:**

```
role: 'admin' | 'lead' | 'designer' | 'stardiz'
```

`stardiz` для прав использует логику `lead`, но ему доступен `/designer` для своего портрета (включая собственную грейдировку).

**Критерий приёмки:** админ может назначить роль stardiz; такой пользователь видит и `/lead/*` (оценивает других), и `/designer/*` (свой портрет/история).

### 11.4. Phase 9 — Подгрузка перформанса в оценку

К каждой форме оценки (`/lead/assess?id=X`) подгружать внешние метрики дизайнера за прошедший период:

- Часы по проектам (из учёта времени)
- Скорость / итерации правок
- NPS / отзывы клиентов
- Выполнение OKR / целей

**Источник данных:** API-интеграция с системой учёта (название уточнит Pavel) либо ручной импорт CSV. На MVP-этапе — выделенный блок «Перформанс» в боковой панели формы оценки, лид видит цифры рядом со скиллами и опирается на них при выставлении уровней.

**Критерий приёмки:** на форме оценки есть отдельный блок с фактическими метриками за период; лид видит их параллельно матрице скиллов.

### 11.5. Phase 10 — ИПР (индивидуальный план развития)

ИПР — структурированный документ роста, который лид (или стардиз) составляет для дизайнера. Привязан к одной или нескольким опубликованным оценкам.

**Состав ИПР:**

- **Цель грейда** на следующий цикл (например, «дойти до Мидл за 6 месяцев»)
- **Сильные стороны** — что хорошо получается (импорт из портрета — последняя оценка)
- **Зоны роста** — конкретные навыки/группы, которые нужно подтянуть
- **Шаги** — список задач/практик с дедлайнами и статусом (todo / in-progress / done)
- **Чек-ин даты** — когда лид со стардизом смотрят прогресс

**Видимость:** дизайнер видит свой ИПР и может отмечать шаги выполненными; лид/стардиз — редактирует. История ИПР сохраняется по циклам.

**Модель данных (черновик):**

```
DevelopmentPlan { id, designerId, authorId (lead/stardiz),
                  cycleLabel, targetGrade,
                  strengths: text, growthAreas: text,
                  createdAt, updatedAt, status }
DevelopmentPlanStep { id, planId, title, description, dueAt,
                      status, doneAt, comment }
```

**Критерий приёмки:** лид/стардиз создаёт ИПР, добавляет шаги, дизайнер видит свой ИПР в `/designer/development-plan` и отмечает шаги.

### 11.6. Phase 11 — Персональная карточка (как в Buildin)

Раздел `/designer/profile` (свой) и `/lead/portrait?id=X` (просмотр) дополняется блоками:

- **Краткая инфо**: дата рождения, город, часовой пояс, стаж в Иде, запущенные часы, лид, лид PM, руководитель отдела, HR, соцсети
- **Грейдирование** — список циклов с переходом в детальный портрет (есть)
- **Кроксы (награды)** — персональная доска почёта. Каждая награда: иконка + название + дата + краткий текст. На hover — раскрытие с расшифровкой (как в PDF-примере: «FIRST UPGRADE — закрыт испытательный срок», «2025 BEHIND — самой яркой звёздочкой 2025 года»)
- **Команда лида** — другие дизайнеры этого лида (chips с аватарами)
- **Проекты** — список с часами и годами

**Награды:**

```
Award      { id, code (unique), name, hint, iconUrl, description }
UserAward  { id, userId, awardId, grantedAt, comment }
```

Каталог наград админ заполняет вручную, выдаёт в админке через `/admin/awards` или прямо на карточке пользователя.

**Подвал страницы:** «Немного о себе» — свободный markdown-текст, редактирует сам пользователь.

**Критерий приёмки:** дизайнер видит свою карточку в стиле IDA-buildin, переход с грейдов работает, hover на наградах раскрывает описания.

### 11.7. Phase 12 — Расширенный аудит-лог

Текущий `AuditLog` фиксирует только изменения `gradeFloor` (PRD §6.3). Расширяется до полного audit trail:

- Изменения матрицы (создание/архив скиллов, правка весов и порогов)
- Публикация и удаление оценок
- Изменение ролей пользователей, отделов, лидов
- Создание/обновление ИПР

**Что фиксируем:** `actorId`, `action`, `target` (тип + id), `before`, `after`, `at`, `comment`.

UI: `/admin/audit` — фильтрация по actor / target / типу события / дате. Уже есть в навигации, но фактически ничего не показывает кроме grade_floor.

**Критерий приёмки:** любое изменение, влияющее на расчёты или права, отражено в аудит-логе с возможностью отмотать «кто, когда, что и почему».

### 11.8. Phase 13 — Перевод UI на «Ида.Продукты»

Перевести текущую визуальную систему (Base44 / Canvas Pearl / lime accent) на корпоративный UI-kit «Ида.Продукты».

**Что включает:** компоненты, токены, типографика, иконки и общие layout-паттерны IDA.

**Подход:** ждём от Pavel описание / ссылки на Figma и UI-kit, после чего ребрендуем токены и компоненты по очереди — без изменения функциональности.

**Критерий приёмки:** все экраны выглядят как часть IDA-продуктовой линейки, переключения между этим продуктом и другими IDA-сервисами не вызывают визуального дискомфорта.

### 11.9. Интеграция в Ида.Тимс — отдельный трек

Внутренний интранет Ида.Тимс становится точкой входа: профили, разделы и навигация живут там, грейды-приложение либо встроено как раздел, либо синхронизируется по API. Детали и приоритет — после Phase 6–7. В этом PRD не описывается отдельной фазой; визуально мы будем равняться на Тимс при ребрендинге (Phase 13).
