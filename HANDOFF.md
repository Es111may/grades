## Что это за проект

Веб-приложение для грейдирования дизайнеров в IDA Project. Заменяет Excel-шаблон. ~25 человек: 3 лида + 2 стардиза + 20 дизайнеров + 1 админ (Pavel).

- **Repo:** `git@github.com:Es111may/grades.git` (main = prod)
- **Деплой:** Railway, авто-деплой при push в main
- **Стек:** Next.js 14 App Router + TypeScript + Tailwind + Prisma 5 + Postgres + NextAuth

13. **Phase 25 — связка с Я.Календарём (идея Pavel 17.09.2026, продумать).**
    Две стороны, и они очень разной стоимости — разносить их обязательно.
    - **Грейды → Календарь (дёшево, без интеграции).** Кнопка «Поставить
      встречу» рядом с датой грейдирования: deep-link на создание события в
      Я.Календаре с подставленным названием («Грейдирование — Имя»), датой и
      участниками, плюс скачивание `.ics` как запасной вариант для любого
      календаря. Никакой авторизации, никаких секретов, делается за день.
      Этим и стоит начинать.
    - **Календарь → Грейды (дорого, нужен доступ уровня организации).**
      Программный интерфейс у Я.Календаря — CalDAV (`caldav.yandex.ru`).
      Личный CalDAV требует **пароля приложения от каждого лида** — это
      нерабочий вариант: мы не собираем чужие пароли. Значит нужен доступ
      через Яндекс 360 для организаций (сервисный доступ/OAuth), а это
      вопрос к админу домена, не к разработке. Пуш-уведомлений у CalDAV нет,
      так что синхронизация — это опрос по расписанию.
    - **Чем сопоставлять событие с дизайнером.** Название («Грейдирование —
      Имя») ненадёжно: переименуют и связь порвётся. Правильнее — создавать
      событие самим и хранить его UID рядом с планом грейдирования; тогда
      перенос встречи читается однозначно.
    - **Схему придётся тронуть.** Сейчас `nextGradingAt` — это дата без
      времени. Для календаря нужны время и таймзона, иначе встреча всегда
      будет вставать в полночь.
    - **Чей срок главный.** Если встречу перенесли в календаре, победителем
      логично считать календарь — он ближе к реальности. На «проведено» это
      не влияет: оно и так выводится из опубликованной оценки, а не из даты
      (см. `src/lib/gradingPlan.ts`).

      «Грейдирование назначено на 12 нояб. 2026 · лид Ирина Белова».
    - **HRD — о завершении грейдов.** Когда лид публикует оценку, HRD
      получает сообщение с итогом: кто, какой грейд и изменился ли он.
      Например: «Ирина Белова · Мидл → Мидл+».
      - Срабатывает на публикацию оценки (`publish` в API оценок).
      - Кто HRD, задаётся в настройках (email), а не в коде.

    Общее:
    - **Точки срабатывания:** для дизайнера — сохранение даты
      (`api/users/[id]/grading-date`, `GradingDateEditor` в
      `GradingPlanChip.tsx`); для HRD — публикация оценки.
    - **Канал:** бот-аккаунт Mattermost, токен в переменных Railway. Личный
      канал открывается через `/api/v4/channels/direct`, сообщение уходит
      через `/api/v4/posts`. Человека ищем по рабочему email.
    - **Решить до работы:**
      - писать ли при переносе даты и при её снятии;
      - класть ли в сообщение ссылку на портрет;
      - кто заведёт бота и выдаст токен (админ Mattermost);
      - писать ли заодно лиду;
      - HRD: писать после каждой оценки или одной сводкой в конце цикла;
      - HRD: включать ли XP, ставку, вилку и ссылку на портрет.

## Договорённости по стилю кода

- **Через primitives.** Не плодить `bg-white border border-cloud rounded-card` — пиши `card`. Не плодить `bg-lime border ...` — пиши `btn-accent`. Кастомизация — через override классов, не через новый набор.
- **`font-display`** только для больших заголовков (h1, h2, KPI). Обычный текст — body.
- **Tabular-nums** на всех числах в таблицах.
- **Системные акценты** (emerald/sunset/blaze/sky) — для семантики (success/warn/danger/focus). Брендовый — lime.
- **Без uppercase tracking-widest** — Pavel однажды попросил убрать глобально (старая привычка из ранних фаз).
- **`.chip-build` мельче `.chip-neutral`** (10px vs 11px) — билд второстепенен в плотных списках. Но на странице оценки и портрете билд вёрстан inline-чипом `.chip-neutral` с точкой внутри — там размеры равны.
- **Иконки** — только из `components/icons.tsx`, не плодить inline-SVG.

  всё равно зовёт `npm install`, но с lock версии фиксированы. Строгий
  `npm ci` — переменная Railway `RAILPACK_NODE_NPM_INSTALL="npm ci"` (не
  включали). Зависимости меняем только через `npm install <pkg>` в
  `grades-app/`, lock коммитим вместе с `package.json`.

## Подводные камни

1. **Render-cache миграций.** При перезапуске контейнера флаги в `oneTimeMigrations.ts` сбрасываются — миграции отрабатывают повторно (идемпотентно). ОК.
2. **JWT-сессия NextAuth** хранит fullName/role на 8 часов. AppHeader тянет fresh данные из БД на каждом SSR-рендере (чтоб правки админа сразу появлялись).
3. **Stardiz** не имеет своего портрета (нет в `/designer/*`). У него только доступ к `/admin/users` (только свои подопечные) и к форме оценки.

5. **Грейды:** `intern` удалён, `premiddle` добавлен. Пороги XP: `0/75/105/135/180/230` (могут отличаться по билду).
6. **ExcludedEmail** — единственный механизм блокировки воссоздания удалённых через seed/import-team. И seed, и import-team уважают этот список.
7. **Тесты `grade.test.ts` теперь зелёные** — Phase 24 закрыта 03.10.2026 (накопительные гейты). Красных тестов в проекте больше нет — новый красный тест означает регрессию.
