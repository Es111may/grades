Плюс системные пробелы HR-портала:

- **Грейды заполнены у 24 из 122** (20%). Логично: система грейдирования — это
  Грейды, а не HR-портал. Грейд остаётся за нами.
- `employee_dismissalemployeelog` — таблица периодов занятости **пуста (0 строк)**.
  То есть возвраты в команду HR не ведёт вообще, и кейс Ани Бадыревой оттуда
  не вытащить никогда.
- `is_archive` **не согласован** с датой увольнения: у Бадыревой и Литвиновой
  есть дата ухода при `is_archive=0`. Признак «ушёл» надо брать из
  `date_of_dismissal`, не из `is_archive`.
- Причина ухода заполнена у 50 из 76 архивных (66%).
- **3 записи о ставках имеют дату в будущем** (максимум `2026-10-08`) — это
  запланированные повышения. При расчёте текущей з/п обязателен фильтр
  `date_start <= today()`, иначе ФОТ покажет будущее.
- **Почасовка в HR не размечена.** `work_format` — это не тип оплаты (значения
  0/1 распределены 74/48, у Егора Коровина `work_format=1` и при этом
  `salary=104 939`). Флаг почасовой оплаты придётся вести в Грейдах.
- История ставок покрывает **47 человек из 122**. Твоя колонка «Прогрессия»
  («повысили 60 → 90 → 130») местами богаче, чем лог HR.

### Следствие: не «синхронизация», а «сверка»

Прямой синк «затираем своим из HR» недопустим — Оксана снова станет 120,
а Бадырева уволенной. Поэтому:

1. Синк **заполняет только пустое** в Грейдах.
2. При расхождении **ничего не затирает**, а показывает экран
   **«Расхождения с HR-порталом»**: «HR: 120 000 · Грейды: 130 000 · выбрать».
3. Каждое поле помнит, откуда пришло (`source: hr | manual`), и ручное значение
   синк больше не перетирает.

Это дороже одного скрипта, но иначе твои правки будут молча пропадать при каждом
запуске — а деньги молча пропадать не должны.

## 4. Модель данных

### 4.1 Периоды занятости вместо пары дат

Аня Бадырева ушла и вернулась — значит одной пары `hiredAt` / `leftAt` не хватает.

```
EmploymentPeriod
  userId        Int
  startedAt     Date
  endedAt       Date?
  exitReason    String?   // код из справочника HR
  exitInitiator String?   // 'employee' | 'company'
  exitNote      String?   // свободный текст: «ушла в Т-банк»
  source        String    // hr | manual
```

- Стаж = сумма закрытых периодов + текущий
- «В команде сейчас» = есть период без `endedAt`
- «Всего людей за всё время» = уникальные люди, **не** периоды
- «Возвращался» = периодов больше одного — отдельный чип в карточке

`hiredAt` на `User` остаётся (на нём висит существующий код), но становится
зеркалом первого периода.

### 4.2 Почасовая оплата

```
employmentType  String   // 'monthly' | 'hourly'
hourlyRate      Int?     // ₽/час, для почасовых
```

Почасовые (Алина, Егор) **исключаются** из СЗП, МЗП и проверки вилок — иначе они
ломают средние, как ломает сейчас з/п 0 в твоей таблице. В ФОТ входят по факту.
Ты сказал Алину можно не учитывать — сделаю мягче: она остаётся в реестре и в
«за всё время», но помечена почасовой и не попадает в средние.

### 4.3 История ставок

```
SalaryRecord
  userId        Int
  amount        Int       // ₽/мес, «на руки» (до налогового навеса)
  effectiveFrom Date
  kind          String    // hire | raise | correction | probation_end
  source        String    // hr | manual | xlsx
  note          String?
  createdById   Int?
```

Из неё считается всё, что ты сейчас ведёшь пятью колонками: текущая ставка,
дата последнего повышения, прогрессия, ставка на начало года, % роста,
изменение в рублях и средневзвешенная за год. Твоя формула на 40 строк
(`LET` + `MAP` + `LAMBDA` в `C14`) становится обычным серверным расчётом.

**Важно:** при расчёте текущей ставки фильтр `effectiveFrom <= сегодня` —
в HR лежат 3 будущих повышения.

### 4.4 Трек и роль доступа

```
role  += 'staff'                                       // доступ
track  = 'design' | 'ba' | 'ux_writer' | 'research'    // специализация
```

БА, UX-редакторы и исследователи получают `role='staff'`. Причина: в коде ~20
мест проверяют `role === 'designer' || role === 'stardiz'` в смысле
«грейдируемый», и `staff` автоматически не попадёт ни в лидерборд, ни в 9-Box,
ни в формы оценки — **ни одну проверку менять не нужно**. Плюс
`getDashboardForRole` для неизвестной роли уже отдаёт `AccessDenied`, поэтому
они **не смогут войти** — ровно как ты решил («пока только записи»).

Трек берём из `employee_position` HR-портала автоматически.

### 4.5 Вилки

```
SalaryBand
  track, key (junior … senior | stardiz | lead | probation)
  min, max, effectiveFrom, note
```

История нужна, чтобы вилки 2025 и 2026 не перетирали друг друга — иначе YoY
сравнивает старые ставки с новыми границами.

Ты фиксируешь попадание в вилку цветом — в сервисе это станет вычисляемым
состоянием: **в вилке** (зелёный) · **ниже** (синий, недоплата) · **выше**
(красный) · **вилка не задана** (серый). Не заливка руками, а следствие данных.

### 4.6 Настройки

`Setting` — key-value: `payrollTaxRate = 0.36` (налоговый навес), редактируется
админом. Не в коде: ставка меняется, и это не НДФЛ в чистом виде, а НДФЛ +
взносы.

## 6. Удаление или деактивация

Ты спросил — да, логика меняется, но не полностью запрещает удаление.

**Правило:** жёсткое удаление разрешено только для записей **без истории** —
опечаток и дублей. Запрещено, если у человека есть хотя бы одно из:
закрытый период занятости, запись о ставке, опубликованная оценка, заметка.
В этом случае кнопка «Удалить» дизейблится с подсказкой «У человека есть
история — доступна только деактивация».

Причина простая: hard delete ломает «сколько всего людей было за всё время» и
YoY-историю, а это ровно то, что ты просил считать. `ExcludedEmail` (чёрный
список, чтобы удалённый не вернулся автоимпортом) остаётся для опечаток.

**Фильтр в «Команде»:** `Активные · Ушедшие · Все`, по умолчанию «Активные»,
состояние в URL. Сейчас страница грузит всех подряд с `orderBy: active desc`,
без фильтра — а реестр вырастет с ~33 до 122 человек, так что фильтр
обязателен, а не желателен. Ушедшие показываются приглушённо, с датой и
причиной ухода.

## 7. Раздел «Экономика» (только админ)

Маршрут `/admin/economics`.

**Расшифровка твоих сокращений** (сверил по формулам дэшборда):
СЗП — средняя ставка · МЗП — медианная · **ССЗП — средняя стартовая** (по
нанятым в этом году, то есть цена найма) · ФОТ — сумма ставок ·
**CГПЗП / ГПЗП** — средний и суммарный годовой прирост в рублях ·
**«За год»** — средняя, взвешенная по времени.

**Блоки:**
1. Сводка сейчас: Человек · ФОТ/мес · СЗП · МЗП · Потолок, каждая с YoY
2. По грейдам: вилка, СЗП, МЗП, человек, ФОТ, доля ФОТ, YoY, сколько вне вилки
3. По отделам (Криэйт / Импрув / Инхаус / Лиды) + ССЗП новых наймов + прирост
4. По направлениям внутри Инхауса (Продукт / R&D / Коммуникации)
5. Динамика ФОТ и численности по месяцам
6. Найм и уход: наймы, уходы, attrition, ССЗП новых, разбивка причин
   **по инициатору** (сотрудник / компания) и подкатегориям

## 10. Риски

1. **Ставки — новый класс чувствительных данных.** Серверная фильтрация полей,
   ни одной ставки в client-бандле, audit-log на запись. Отдельно проверить
   «Войти как»: убедиться, что `impersonatorId` не даёт админских прав внутри
   сессии подставленного пользователя.
2. **Вилки устарели** → алерты «дороже вилки» загорятся почти у всех.
   Пре-мидл получает в среднем 120,7 при верхней границе вилки 100; Джун — 88,3
   при 75. Джун+ и Пре-мидл обе `75-100`, Мидл+ и Пре-синьор обе `120-140`.
   **Сначала пересборка вилок, потом включение алертов.**
3. **HR-портал read-only.** Мы не можем починить данные в нём — только показать
   расхождение. Значит часть правок навсегда останется ручной в Грейдах
   (возвраты, почасовка, Рита Алексеева, которой в HR нет).
4. **Зависимость от доступности ClickHouse.** `chQuery` уже сделан
   отказоустойчиво (таймаут 6 с, ошибка не валит страницу) — сверка должна
   работать так же: недоступен HR → показываем последние синхронизированные
   значения и метку «данные от такой-то даты», а не пустоту.
5. **`prisma db push` без миграций.** Добавление nullable-колонок и новых
   таблиц безопасно. Email оставляем обязательным — в HR он есть у 122/122,
   так что необязательность не нужна. Уникальный индекс не трогаем.
6. **Реестр вырастет с ~33 до 122** → фильтры обязательны, вероятно нужна
